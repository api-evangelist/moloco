# Serve and track a Moloco Commerce Media ad

The serving loop for a retailer or marketplace running its own retail-media network.

## Auth and hosts

- Every Decision and Event call authenticates with `x-api-key: $API_KEY` — a **platform-scoped** key
  generated by a Platform Owner in the Standalone Campaign Manager under Developer → Credential Management.
  Keys are shown once at creation and are not retrievable afterwards.
- `platform_id` is a path parameter on every operation; Moloco issues it during onboarding.
- The published hosts are `sandbox-dcsn.mcm-api.moloco.com` (decision) and `sandbox-evt.mcm-api.moloco.com`
  (events). Moloco supplies the correct regional host for your platform — the docs state the host varies by
  platform.

## 1. Request a decision

Pick the operation that matches the ad format:

| Format | Operation | Path |
|---|---|---|
| Sponsored Products | `RmpDecisionApi_DecideAdProducts` | `POST /rmp/decision/v1/platforms/{platform_id}/product-auction` |
| Sponsored Display | `RmpDecisionApi_DecideAdDisplay` | `POST /rmp/decision/v1/platforms/{platform_id}/display-auction` |
| Sponsored Brands | `RmpDecisionApi_DecideAdBrands` | `POST /rmp/decision/v1/platforms/{platform_id}/brand-auction` |
| Reserved Display | `RmpDecisionApi_DecideAdReservedDisplay` | `POST /rmp/decision/v1/platforms/{platform_id}/reserved-display-ads` |

Send the user context, the inventory/placement, and — where you must limit personal-data processing — the
`personalization_mode` field: `STANDARD`, `METRIC_ONLY` (contextual ads plus attribution, no personalization
or model training) or `ID_LESS` (no user id, contextual ads only).

This is a latency-sensitive path. Implement graceful fallback: if the decision call fails or times out,
render your organic result rather than blocking the page.

## 2. Fire the trackers

The decision response carries impression and click tracker URLs per ad. Fire them exactly as returned —
impression on render, click on click. Attribution and billing both depend on it.

## 3. Post the user events

`RmpEventApi_PostUserEvent` — `POST /rmp/event/v1/platforms/{platform}/userevents`. Send the shopper's
first-party events (home, page view, item view, search, add to cart, purchase and the rest of the published
event taxonomy). This is what the models source and score against; an ad platform with no event stream
ranks on nothing.

At least one user identifier must be present — `user_id`, `device.persistent_id` or `custom_id` — or the
call returns 400 "no available valid identifier to construct Moloco advertising ID".

## 4. Errors and throttling

The Decision and Event APIs both declare 400 / 401 / 403 / 404 / 429 / 500. Payloads are JSON-serialized
gRPC status objects — **read the HTTP status and the `message` field, ignore `code` and `details`**. A 429
is "too many requests either by platform or by user"; no numeric quota is published, so back off
exponentially. See `errors/moloco-problem-types.yml` and `rate-limits/moloco-rate-limits.yml`.

## 5. Pulling items out of serving

`RmpManagementApi_UpdateItemStatusBulk` (Management API) is the item kill switch — immediate bulk removal of
specified items from ad serving. Use it for recalls and out-of-stock, not the campaign pause path.
